## Ключевые решения целевой архитектуры

- **Ядро - событийная шина**: Kafka + Schema Registry (каталог схем, контрактная валидация) + DLQ. Домены взаимодействуют только через события - это и есть целевое состояние «слабосвязанная событийная платформа».
- **Легаси - только «мосты совместимости»** (пунктир на диаграммах): CDC (Debezium) тянет изменения из DWH на SQL Server 2008, ACL-адаптер переводит Camel-маршруты ESB в доменные события. Power BI заменяется витриной, PowerBuilder остаётся у мед. зоны. Всё легаси выводится к 3-му году.
- **Медицинские данные вне витрины**: медкарты, истории болезни, снимки и результаты исследований живут в изолированной медицинской зоне (доступ - только ИИ-сервисы). Витрина строится на данных, которые бизнесу и разрешено видеть.
- **Два пути данных**: streaming (Kafka -> Flink -> ClickHouse, near real-time) и micro-batch (зеркало событий в data-озеро -> dbt -> ClickHouse). Medallion-слои в dbt, единые метрики в семантическом слое.
- **Витрина**: Superset + семантический слой + RBAC/RLS через OIDC. Пользователь видит отчёты в рамках своего уровня доступа и строит свои отчёты по единым метрикам.
- **Масштабирование - без изменения ядра**: новые домены (фармкомпании, медэлектроника) подключаются по тем же событийным принципам и приносят свои data-продукты. Новые регионы (2–3) - те же компоненты, изоляция по data residency.
- **Облако - Yandex Cloud** (managed Kafka, Managed ClickHouse, Data Lake / YOS, IAM).

## Связь со стадиями трансформации

| Стадия | Что происходит | Риски, закрываемые на этой стадии |
|--------|----------------|-----------------------------------|
| 0–6 мес. | Пилот в 1–2 доменах (финансовые расчёты / пациентский поток), единые принципы событий, DLQ, каталог схем | R1, R2, R12 |
| 6–18 мес. | Развёртывание на критичных доменах, streaming-витрина, ACL на интеграциях Camel/DWH | R5, R6, R9 |
| 18–36 мес. | Вывод точечных синхронных интеграций, доменная потоковая аналитика, новые домены и регионы | R10, R11, R13, R16 |
