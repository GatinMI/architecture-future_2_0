# Обоснование событийного подхода (vs шина Camel + DWH)

## Как устроено сейчас и где болит

Текущий ландшафт (см. data_flow.png):

- **DWH на SQL Server 2008** - монолитный центр: в представлениях и хранимых процедурах зашита бизнес-логика нескольких доменов (клиенты, финансы, клиники), туда же пишутся медицинские данные из операторского интерфейса PowerBuilder. Power BI тянет отчёты прямо из DWH.
- **ESB на Apache Camel** - точечные синхронные интеграции: маршруты «DWH -> ИИ», «DWH -> финтех», «внутренние сервисы -> DWH». Каждая новая связка - новый маршрут, написанный под конкретного потребителя.

Практические последствия:

1. **Новое направление = новый маршрут + новая логика в DWH.** Интеграция фармкомпаний или медэлектроники (планы компании) без DWH-трансформаций и Camel-маршрута невозможна - а DWH уже является тем самым местом, куда «не должны» приносить большие объёмы бизнес-логики (требование руководства).
2. **Синхронная связка = взаимная зависимость.** Если потребитель Camel-маршрута тормозит или падает, страдает производительность самого источника; упал конвейер «внутренние сервисы -> DWH» - деградирует DWH для всех, включая BI.
3. **Time-to-market отчётности - часы.** Сложные отчёты собираются долгими SQL поверх сотен ТБ в одной базе; добавление отчёта = новая трансформация в DWH + ожидание ETL.
4. **Одна база на все домены** = единая точка конкуренции: изменение схемы под один домен - риск для всех остальных; нагрузочные профили (OLTP-запись из клиник и тяжёлый BI-анализ) конкурируют за ресурс.
5. **Нет контрактов и версионности.** Схемы Camel-маршрутов и DWH-представлений не описаны договорённостями: потребители узнают об изменениях на продакшене.

## Что даёт событийная архитектура

Целевое состояние (Task3Advanced): домены публикуют события в событийный бэкбон (Kafka + Schema Registry + DLQ), потребители подписываются независимо. Преимущества:

### 1. Гибкость (новое направление - без DWH)
- Новый домен или новый потребитель - это **подписка** на существующие события + публикация своих. Источник не знает о потребителях, код и схема источника при этом не меняются.
- Контракт закреплён в каталоге схем (Schema Registry) с правилами совместимости: изменения видны до мерджа, а не на продакшене.
- Фарм и медэлектроника подключаются ровно так же, как финтех: события `PharmaOrderPlaced`, `DeviceRegistered` - и никаких ETL в DWH. Это и есть выполнение требования «интеграция новых бизнес-направлений без значительных объёмов бизнес-логики в DWH».
- Домены становятся самостоятельными: у каждого своя БД, свой релизный цикл, свой владелец (data-продукт).

### 2. Масштабируемость
- Бэкбон масштабируется горизонтально (партиционирование по доменам/сущности), потребители - независимо друг от друга и от источников.
- Сотни ТБ распределяются по слоям: сырые события - в data-озеро (холодное, дёшево), hot-потоки - Flink-агрегаты, аналитика витрины - ClickHouse. Аналитическая нагрузка больше не конкурирует с OLTP-записью клиник и DWH (DWH со временем выводится, а не нагружается).
- Высокочастотные потоки (телеметрия устройств) изолированы в своих топиках - они не мешают другим, «штучным» событиям.

### 3. Скорость реакции (time-to-market)
- Отчёт «сегодня» собирается из витрины (марты + семантический слой), а не из часового ETL по DWH: данные приходят в near real-time (Flink) или micro-batch (dbt), новый отчётный срез - подписка + март, а не миграция DWH.
- Независимые релизы: домен добавляет событие/поле (совместимое) без координации релизов остальных трёх подразделений.
- Отказ потребителя не останавливает бизнес: события накапливаются в топиках (и в DLQ), потребитель поднимается и досматривает (replay). Сейчас падение конечной точки Camel-маршрута рвёт всю цепочку.

### 4. Организационная выгода
- Границы контекстов совпадают с командами/подразделениями: мед (клиники + ИИ), банк (финтех), ГО (отчётность), новые домены - у каждого понятный «владелец событий». Это снижает R7 (data-silos) из Task3Advanced: обмен данными становится договорённостью о каталоге событий, а не переговором о доступах к чужой базе.
- Каталог событий - единый «published language» для регуляторов и аудита (банковская лицензия, медданные): что публикуется, куда и по какой схеме - формализовано.

### 5. Отказоустойчивость и наблюдаемость
- DLQ + мониторинг lag + алерты по SLA свежести - вместо «тихих» ошибок ETL-трансформаций DWH.
- Журнал событий = полная история изменений (реплеи, аудит, отладка расхождения цифр между доменами).

## Чего мы отдаём (честно)

- **Eventual consistency.** Аналитика и отчётность не требуют сильной согласованности: витрина обещает SLA свежести (минуты), а операционные процессы внутри домена остаются транзакционными (своя БД, свои инварианты). Критичные для банка операции (платёж) согласуются внутри финтех-контекста, а не через шину.
- **Дополнительная инфраструктура и навыки.** Kafka, Flink, ClickHouse, data-озеро - это расходы (рассчитаны в TCO, Task5) и дефицит компетенций (риск R8 из Task3Advanced, закрывается наймом/обучением).
- **Сложность распределённой отладки.** Нужны трассировка (correlation_id), каталог схем и дисциплина идемпотентных потребителей - всё это заложено в контракты событий (events.md) и наблюдаемость (Task3Advanced).

## Переход: без остановки бизнеса

- Мосты совместимости (CDC из DWH, ACL-адаптер Camel) публикуют легаси-события в бэкбон - новые потребители уже работают на новых контрактах, пока старое не переедет.
- Dual-run и сверка цифр (dual-run-период) до cutover каждого домена; канареечный переход по доменам (этапы 0–6 / 6–18 / 18–36 из Task3Advanced).
- Риски перехода (R2, R5, R12, R13) и меры - в risk-management-plan.md.

## Вывод

Событийный подход - это не «модный» выбор, а прямая реализация заявленной долгосрочной цели компании: слабосвязанной событийной платформы, где Camel и DWH остаются только «мостами совместимости» на период миграции. Он закрывает два требования руководства (витрина без медданных и интеграция новых направлений без DWH-логики) и сняет главную структурную проблему текущего ландшафта - монолитную DWH как центр и Camel как синхронные точечные связки.
